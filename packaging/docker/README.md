# DST Docker development preview

Run from a Linux host or inside WSL with Docker Engine and Docker Compose available:

```sh
sh bin/dst-docker up
```

Open the authenticated URL printed when the application is ready. Windows users open that URL in their normal browser. Installation and execution stay inside Linux; this path does not download or run the DST Windows installer.

On first setup, use that private installer link to create your owner username and password. There is no shared default password. Later, open the IP address and console port in any browser and sign in normally; the existing Remember me option is available. Owner credentials and sessions persist in the protected configuration volume. The bootstrap can create only the first account, requires the launch key and a same-origin request, and refuses to reopen over an unreadable account store.

The private preview builds DST from this checkout. The first build downloads the Linux base images and frontend dependencies. It runs the application as a non-root user, keeps its filesystem read-only, and persists configuration, state and cache in named volumes. The browser listener accepts the Linux host's IPv4 addresses on port8088 by default, and the launcher prints authenticated links for those addresses as well as localhost. Select another console port with installer `--port PORT`, `sh bin/dst-docker up --port PORT`, or later `sh bin/dst-docker port PORT`. The selected port persists in the configuration volume across upgrades. A busy port produces an error instead of silently switching to another port. Changing it restarts only the management console; game ports and game containers are separate. Authentication and host-only action restrictions remain enforced. Set `DST_HTTP_BIND_ADDRESS=127.0.0.1` before launching to restrict access to localhost. It uses Linux host networking and is not a Docker Desktop/macOS package.

On Windows with WSL NAT networking, the WSL address works from Windows; access through the Windows machine's LAN address additionally needs a Windows forwarding rule. Linux hosts and WSL mirrored networking use their reachable host address directly. A host firewall must permit the selected port for other devices to connect.

## Optional HTTPS for a private IP

After the HTTP console is ready, enable a separate HTTPS address from Linux or WSL:

```sh
sh bin/dst-docker https YOUR_HOST_IPV4
sh bin/dst-docker https-root "$HOME/dst-root.crt"
```

HTTPS uses the chosen console port, normally 8088; a third argument selects another available port. Plain HTTP on that port redirects to HTTPS. The application listens privately on loopback behind the proxy. Enabling HTTPS recreates only the management application and its TLS proxy; game maps and the database remain under their existing controls. Existing owner accounts remain available. Use a stable host address; a WSL NAT address may change when WSL restarts.

The second command exports only the public root certificate and prints its SHA-256 fingerprint. Transfer that certificate to each client PC and verify the fingerprint before explicitly trusting it in that client's certificate store. For Windows Chrome/Edge, the current user's Trusted Root Certification Authorities store is sufficient. Firefox may require its own Authorities import. DST never installs trust automatically and does not ask you to bypass certificate warnings. The private authority keys remain in a dedicated Docker volume, separate from the application and its game data. Preserve that volume across upgrades; deleting it requires clients to trust a replacement authority.

Open the printed `https://HOST_IPV4:8088` address after trust is installed (or use your chosen port). Player compatibility uses manual instructions: after saving settings, DST shows one complete list of required Game.ini and Engine.ini overrides, with Copy and Download instructions actions. Each player closes the game, backs up their files and merges the listed values. DST does not select, upload or modify the player’s local files through Docker.

The launcher retains the HTTPS override outside versioned installer releases and reuses it on subsequent commands. Repeating `https HOST_IPV4 [PORT]` updates the address or public port while preserving the existing authority and owner accounts. `port PORT` changes the secure console port when HTTPS is enabled. This path requires the Docker image built with private HTTPS listener support.

For WSL NAT, `packaging/docker/Enable-DstDockerLan.ps1` configures a specific Windows LAN address and console port from administrator Windows PowerShell. Run it with `-ListenAddress <Windows-LAN-IP>` after the portal starts; it defaults to8088, or accepts `-Port PORT` for your chosen port. `-WhatIf` previews its exact changes. It leaves other forwarding rules intact, limits its firewall rule to the private local subnet, and can be rerun to refresh a changed WSL address.

```sh
sh bin/dst-docker status
sh bin/dst-docker url
sh bin/dst-docker logs
sh bin/dst-docker down
```

Stopping removes the portal containers, preserving named data volumes. Owned game services are managed separately through the portal. Existing Windows/Hyper-V servers remain separate. The local launch token persists in protected configuration across application restarts; retrieve the link with `url`.

## Current behavior

- Settings includes searchable per-map RAM limits in the familiar DST layout. All maps share Docker's available CPU by default; optional per-map CPU caps can be shown and cleared back to shared access. CPU caps are ceilings, not reserved cores, and do not block admission based on their sum. Allocations are changed with the battlegroup stopped; saving never stops it implicitly. Each map instance receives verified Docker limits. Startup and demand scaling check combined RAM with a2 GiB service reserve, leaving another2 GiB host headroom. These controls do not resize WSL or change the host's physical hardware. Interrupted allocation changes remain pending for an explicit retry.

- The existing DST shell, navigation, Server Overview and Players layout connect to the Linux backend. Docker setup occupies the existing Setup Wizard location. The separate early Docker dashboard remains an internal development scaffold.
- Authenticated DST API and browser client, with Linux startup and shared product version.
- Observer reads Docker metadata and memory statistics, publishing a sanitized snapshot every ten seconds. It never accepts commands. The application has no Docker socket mount; the observer has the socket and no network interface. A read-only bind mount of a Docker socket does not itself enforce read-only API access; that boundary is implemented by the observer's fixed GET-only code.
- Explicit stale/unavailable states. Map and container usage is an observation, not a gameplay-ready or login guarantee.
- The derived Deep Desert cache uses the same snapshot and inventory contracts with a native Linux SQLite helper. HTTP cache reads do not query the game database; an active map viewer renews the bounded background collection lease, and collection stops when that lease expires. Hydration and source failures retain the last published snapshot with stale/unavailable status. Public POIs remain unavailable when the source cannot establish their privacy. The cache lives in the private state volume; the helper refuses root execution and unsafe storage paths. Windows keeps its existing helper.
- Overview and Map SpinUp include a saved Memory balancing switch. Off uses the normal startup, stock automatic-map policy and explicit Warm choices; On additionally allows ordinary empty on-demand maps to unload. Changing the switch does not restart the world. Memory admission and occupied-map protection apply in both modes. New installations default to Off.
- Memory Swap is a separate Owner control beside Memory balancing. Low allows 1 GiB of emergency swap per running map; Automatic allows 2 GiB; Custom supports 1–16 GiB per map, a 0–32 GiB managed host pool and swappiness from 0–100 (normally 10). Automatic pool sizing accounts for existing administrator-managed swap and at least two running maps. A zero pool uses existing host swap without creating a file. The review shows the host changes before applying them and preserves at least 25 GiB or 10% of disk space. Map RAM limits stay unchanged. Running maps, newly created maps, resource changes and server updates retain the selected allowance. Disable restores Docker's default additional swap allowance, removes only this installation's managed pool, and restores swappiness only while DST still owns its value. Interrupted changes offer Retry and Restore previous policy. Upgraded maps keep their existing limits until an explicit apply/default restoration; they are not silently resized. Managed host swap requires a rootful Linux Docker Engine with swap accounting and host swap tools, prepared by the installer.
- Optional `DST_OBSERVE_PROJECT` restricts observations to one Compose project. Only official Funcom self-hosting image names are included.
- Independent Valve SteamCMD download of the official Linux self-host package, with image-manifest verification and persistent asset storage.
- Guided creation of a separate PostgreSQL database using the packaged official image. Official schema migration runs only after a persistent, verified backup, with the application database role demoted after migration.
- Native PostgreSQL transport preserves the existing SQL results and transaction behavior. Player workflows reuse the shared validation, maintenance safeguards and existing result semantics. Windows-only endpoints are replaced or excluded explicitly; Docker's dispatcher exposes the native/shared adapters rather than a Windows shell.
- World layout derives all 35 stock maps and partitions from the installed official definition. Generated credentials stay local. The application talks to a typed Unix control service and never receives the Docker socket.
- Owned message queues with independently generated TLS certificates; real TLS verification is tested separately from container health. Durable operation state keeps status available during longer setup work.
- Server Overview uses the existing responsive card layout, current-pod semantics, duration formatting and shared external port checker with the configured Docker ports. Shutdown maps remain in Lifecycle controls and disappear from the Overview table. Failed refreshes keep the last snapshot with a visible error and recover after successful polling.
- The existing File Browser application opens from the usual Web interfaces link. It mounts only this world's Saved volumes, keeps `/srv/UserSettings` as the familiar root, and exposes other prepared maps under `Maps`. Its pinned upstream image runs without root or command execution and binds only to loopback. The launcher loads it and normal world startup reconnects it; file data and its own settings persist separately.
- Native director, gateway, text router and initial game-process adapters use the official images. Their preparation, start and stop controls require the user's local service token.
- The independent native stack has passed a real Windows game-client join and character persistence check. The installed build has also passed real service startup, restart and fresh game-ready heartbeat checks. A historical client session is not claimed as a new client acceptance run for every subsequent build.
- Database-only Start/Stop controls let owners run backups and restore verification while game maps stay stopped. Stopping the database requires stopped battlegroup services and no active backup or restore rehearsal.
- The Database page supports browser import and download, restore verification, checksum-checked deletion, UTC schedules, retention and finished helper-job cleanup. Imports accept trusted PostgreSQL custom archives up to 25 GiB and create a separate unverified backup; they never restore or start the world. Verify restore rehearses the archive in a separate generated database and removes that temporary database after success. Restore still requires an explicit verified backup and confirmation.
- Backup schedules run inside the manager independently of the browser. They use an already-running healthy database and never start the database or maps. Interrupted jobs retain their recorded identity for recovery; cleanup protects current recovery backups and active verification/export jobs.
- Local backup mirror keeps additional checksum-checked copies in a dedicated folder on the Docker host. The launcher prepares `$XDG_STATE_HOME/dst-docker/backups/<installation>` (normally `~/.local/state/dst-docker/backups/<installation>`); choose a different initial folder with `sh bin/dst-docker mirror-folder /absolute/folder`. Run `up` to apply the mount, then enable Local backup mirror in Database. The folder and copies survive installer upgrades. In WSL this is a Linux folder in that distribution; the page displays its exact path. Mirroring runs independently of the browser, never starts the database or maps, and never deletes mirror copies when main backups are pruned. Different existing copies are preserved and reported for review. A failed batch protects its source backups until Retry copy succeeds or Cancel failed batch releases that protection. Keep external copies on a separate disk for protection against host-disk failure.
- World Restart keeps the same battlegroup identity and configuration while deliberately replacing its gameplay database with a fresh schema from the installed official package. It requires a healthy database, players offline, exact confirmation, a fresh rollback archive and independent restore rehearsals. It preserves Docker volumes and keeps an intentionally stopped battlegroup stopped. Interrupted replacement recovers before game access reopens; after publication intent, recovery finishes startup without restoring older data over possible new progress. The rollback shortcut refuses new gameplay records; the normal Restore Backup review remains the explicit way to replace newer progress. Returning-character research audit and backed-up offline recovery use captured pre-reset working recipe pairs and preserve unrelated character JSON. These database and recovery paths have isolated qualification; their in-game effects and future schema compatibility remain separate acceptance checks.
- Authoritative shared server INIs, retail settings and startup values use the existing settings pages with native file transport, backups, conflict detection and readback. Server review works with the battlegroup stopped: a read can start only the isolated settings helper, subject to operation/recovery guards. Server review works independently of player-PC files. After saving, Player compatibility shows the complete saved requirements for both player INI files, including the land-claim timer when enabled. Share the instructions with every player; each player applies them manually while the game is closed. Remove only earlier DST compatibility overrides no longer listed, retaining unrelated settings.
- Scheduled restarts run inside the Docker service independently of the browser, with an explicit time zone, persisted operation identity and overlap protection. The existing opt-in update checkbox dispatches the native update controller when a newer build is available, or a normal restart when current. Unknown versions block before stopping the world. An installed isolated world passed an actual unattended scheduled restart, exact operation/request correlation, fresh game-ready heartbeats and player-portal readiness. Its original disabled schedule was restored afterward. This does not establish compatibility with an unreleased future Funcom version.
- The Land Claim Timer uses the native server INI transport with verified backups. Its matching player Game.ini block is included in the complete manual Player compatibility instructions after saving. Players apply it manually while the game is closed. Server configuration checks do not establish its gameplay effect.
- The usual Update command stages the official package separately, verifies a fresh database backup, runs the official migration, and replaces stopped components while retaining their previous generation and Saved volumes. A running world checks map readiness before publishing its gateway; an intentionally stopped world stays stopped. Recovery uses the recorded jobs and package journal, and refuses to restore a stale database over observed new player progress. Manual same-build application passed on the local running test world; a disposable cluster also passed failure recovery after migration and component replacement. This does not establish compatibility with an unreleased future schema.
- The existing Overview and Commands log exports download ZIP archives through the browser. Battlegroup and operator logs are scoped to this installation, streamed with known credential patterns masked, and accompanied by a report of any unavailable or truncated sources. Each source is limited to 128 MiB; the three newest completed archives are retained.
- Native game adapters include all stock shared authentication values and direct privilege-dropped process execution. Graceful stop signals are confined to the identified game process in its owned container; saved volumes and prior stopped containers survive adapter replacement.
- The game wrapper sets the `dune` user's HOME and XDG configuration path before privilege-dropped startup. Keeping root's HOME caused per-user INI overrides to be skipped; the corrected process and 125-slot setting have actual game-client acceptance.

## Qualification boundaries

Server Settings → Management & recovery includes explicit Regis Tank support for accepted Hagga builds. Enable or disable it only with the battlegroup completely stopped. Changing it replaces the stopped Hagga adapters, preserves their Saved storage and resource limits, and leaves the world stopped. Disable requires acknowledgement because starting the official game without compatibility can remove saved Tanks. Interrupted changes block starts and expose Restore previous Tank setting; reopening the page resumes the recorded operation. Grants retain the online-player Hagga check and require fresh readiness plus verified running compatibility files. Actual isolated activation, disable, failure rollback and manager-restart recovery passed without running a game; gameplay acceptance remains pending.

The installer builds the Linux Tank tools; owners do not run a separate image-build command. Preparation uses only the owner's installed official image, accepted recipes and pinned tools. Its isolated job has no network, Docker socket or Saved mount, and the resulting owned image is independently verified before selection. Update with Tank support uses the usual staged-package, verified-backup and migration transaction, prepares compatible Hagga images before map readiness, and preserves the recorded policy during rollback. Unsupported new builds are rejected before stopping the current world. An intentionally stopped world stays stopped. Future-version and running-game acceptance remain separate checks.

The Docker Commands page uses one Start/Stop/Restart set, explicit Apply Server Settings, Update Server, Update with Tank support and the two log exports. Its default sections are Battlegroup, Server updates and Tools. Saved custom names and placements survive normalization of the old VM aliases. Authenticated Docker owners can stop the battlegroup, download their installation's logs and customize the layout through the console's IP address; Windows remote-command rules remain unchanged.

File Browser opens through the authenticated console address and port. Each request requires owner access; the file helper remains loopback-only, unprivileged and limited to this world's Saved storage. Opening it can start only the helper while the battlegroup remains stopped. Streaming upload/download, range requests and resumable transfers have isolated Chromium/Firefox qualification. Ordinary console logout also revokes file access. This adapter has been applied to the local management console and remains private development work.

Battlegroup Director also opens through the authenticated console address and port. Its native page, assets and browser requests stay under the Director path; the link does not point at the viewer's localhost. The proxy accepts only this world's verified loopback Director binding, keeps console credentials out of upstream requests, and blocks control requests during server operations or pending recovery. Opening the page does not start a stopped battlegroup.

This is a private Docker build for local acceptance, not a published release. The standalone shell installer has passed isolated Ubuntu installation and repeat upgrades. Native backup/restore and interrupted-restore recovery, automatic demand/idle map lifecycle, memory admission, native Atlas observations and browser transports have local qualification. The catalogue includes all 35 stock maps; representative Deep Desert, town, story and dungeon maps were started with verified limits and fresh readiness. This is not a claim that all 35 maps or every unchanged gameplay action were replayed.

The 458-route released baseline is retained for the parity audit. The current dispatcher and explicit replacement/removal decisions account for every baseline route, including the Windows terminal WebSocket. Route coverage establishes transport disposition; it does not by itself establish gameplay effects. Existing PostgreSQL gameplay logic is reused. A fresh human game-client join and ordinary travel on the accepted build remain distinct from automated server readiness. Tank gameplay acceptance and compatibility with unknown future Funcom versions are not established by isolated preparation and recovery checks.

Solo stays in the standalone Windows DST application; Docker hosts servers on native Linux and WSL. Distribution uses one shell install command, followed by setup in the browser. The packaged script contains its source: run `bash ./dst-docker-install-current.sh` after obtaining the private build, optionally adding `--port PORT` or `--prefix DIRECTORY`. No public download endpoint is published. VM-data import and Discord portal login remain deferred.

This work is available only in the private repository; no public Docker release or download endpoint has been published. Do not present the preview as production-ready or claim Defender results or comparative memory savings without measurement.
